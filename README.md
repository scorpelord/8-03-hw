### Обоснование выбора (CI/CD)

На основе сравнительного анализа в качестве основного решения предлагается использовать **GitLab CI/CD (SaaS)**.

**Почему GitLab CI/CD?**

1.  **Всё в одном:** GitLab предоставляет единую платформу для хранения кода (Git-репозитории) и CI/CD-пайплайнов. Это упрощает интеграцию и снижает количество разнородных систем, которые нужно администрировать.

2.  **Полное соответствие требованиям:**
    *   Поддерживает запуск сборок как по событиям (push, MR), так и вручную (по кнопке) с передачей параметров.
    *   Позволяет гибко настраивать конфигурации через шаблоны (`include`, `extends`), что критично для микросервисов с похожей структурой.
    *   Обеспечивает безопасное хранение секретов (CI/CD Variables) с возможностью маскирования в логах.

3.  **Гибкость инфраструктуры:**
    *   Возможность использовать **собственные Docker-образы** для сборки (указание `image:` в каждом job'е).
    *   Поддержка **собственных раннеров (GitLab Runners)** — можно развернуть агенты на своих серверах, что важно для безопасности и скорости, если не хотите отдавать код на выполнение в облако провайдера.

4.  **Масштабирование:** Раннеры могут работать в режиме Docker или Kubernetes, обеспечивая параллельный запуск множества сборок и тестов, что критично для микросервисной архитектуры с большим количеством сервисов.

**Почему не другие варианты?**

*   **GitHub Actions:** Это отличное решение, если компания уже использует GitHub для хранения кода. Однако GitLab предоставляет более тесную интеграцию "репозиторий + CI/CD" и часто считается более зрелым решением для сложных пайплайнов в enterprise-среде. Выбор между ними часто сводится к предпочтениям команды.
*   **Jenkins:** Jenkins — это мощный и гибкий инструмент, но он требует значительно больше усилий на администрирование (обновление плагинов, настройка безопасности, бэкапы). GitLab CI/CD как облачный сервис снимает эти заботы, позволяя команде сосредоточиться на разработке.

### Обоснование выбора (Логи)

На основе сравнительного анализа в качестве основного решения предлагается использовать **ELK Stack (Elasticsearch + Logstash + Kibana) с FileBeat**.

**Почему ELK Stack?**

1.  **Минимальные требования к приложениям:** Приложения пишут логи просто в stdout/stderr. FileBeat на каждом узле собирает их и отправляет в центральное хранилище — приложения ничего не знают о системе сбора логов.

2.  **Гарантированная доставка:** FileBeat сохраняет состояние прочитанных файлов и может временно хранить логи на диске, если Elasticsearch недоступен. Это обеспечивает надежность доставки.

3.  **Мощный поиск и аналитика:** Kibana предоставляет богатые возможности поиска, фильтрации и визуализации. Разработчики могут:
    *   Искать по любому полю лога.
    *   Строить сложные запросы с регулярными выражениями.
    *   Сохранять запросы и делиться ссылками на них (требование задачи).

4.  **Зрелость и сообщество:** ELK — это индустриальный стандарт для сбора логов. Существует огромное количество документации, готовых решений и интеграций. Любая проблема, скорее всего, уже кем-то решена.

**Почему не другие варианты?**

*   **Grafana Loki:** Loki — легковесное и экономичное решение, но он оптимизирован в первую очередь для хранения логов и индексации по лейблам, а не для полнотекстового поиска. Если нужен сложный поиск по содержимому логов (как в Kibana), ELK предпочтительнее.
*   **ClickHouse + Vector:** ClickHouse — это супер-быстрое хранилище, но для него потребуется самостоятельно собирать интерфейс для разработчиков (Grafana с плагином или Tabix). ELK дает готовый, удобный UI (Kibana) из коробки, что критично для предоставления доступа разработчикам.

**2. VictoriaMetrics + Grafana**
*   **Сбор метрик с хостов:**  Да (совместим с экспортерами Prometheus).

**3. Zabbix**
*   **Сбор метрик с хостов:**  Да (агенты Zabbix).
*   **Сбор метрик ресурсов хостов:**  Да.

### Обоснование выбора (Мониторинг)

На основе сравнительного анализа в качестве основного решения предлагается использовать связку **Prometheus + Grafana**.

**Почему Prometheus + Grafana?**

1.  **Сбор всех типов метрик:**
    *   **Хосты:** Prometheus собирает метрики с Node Exporter (CPU, RAM, диск, сеть).
    *   **Сервисы:** Для контейнеров используется cAdvisor (метрики потребления ресурсов каждым контейнером).
    *   **Бизнес-метрики:** Prometheus имеет клиентские библиотеки для всех популярных языков программирования (Go, Java, Python, Ruby и др.), позволяя разработчикам экспортировать специфичные для сервиса метрики (количество заказов, размер очереди, время ответа БД).

2.  **Гибкий язык запросов (PromQL):** PromQL позволяет агрегировать, фильтровать и математически обрабатывать метрики прямо в момент запроса. Это дает возможность строить сложные вычисления (например, 95-й перцентиль времени ответа или скорость роста ошибок).

3.  **Лучшая визуализация (Grafana):** Grafana — это стандарт де-факто для визуализации метрик. Она позволяет:
    *   Создавать дашборды с любыми графиками и таблицами.
    *   Делать запросы к данным в реальном времени.
    *   Настраивать панели для разных команд (SRE, разработчики, менеджмент).
    *   Делиться дашбордами и сохранять их в Git как код.

4.  **Модель pull:** Prometheus сам "забирает" метрики с эндпоинтов, что упрощает обнаружение сервисов (service discovery) в Kubernetes и динамических средах.

**Почему не другие варианты?**

*   **VictoriaMetrics:** Это отличное решение, которое полностью совместимо с Prometheus, но предлагает более эффективное хранение данных. Если объем метрик огромен, VictoriaMetrics может быть выбрана как хранилище вместо Prometheus, сохраняя при этом все преимущества сбора через экспортеры и визуализации в Grafana.
*   **Zabbix:** Zabbix — классический инструмент для мониторинга инфраструктуры, но он менее гибок для сбора специфичных метрик приложений. В мире микросервисов, где разработчики сами хотят определять метрики своих сервисов, подход Prometheus с клиентскими библиотеками более удобен и принят сообществом.
